## A. 解除「从页面获取」对平台的硬依赖

### A0 现状（证据）
- 元素抽屉「从页面获取」onClick 首先 `if (!platformProjectContext(project.id)) { message.error(...); return; }`，然后要求已选环境才打开采集弹窗（`src/pages/ElementsPage.tsx`）。
- 采集面板 `ElementPickerPanel` 全部走平台 API（createDebugSession / enableElementPicker / getPickerCaptures / previewPickerCandidate / confirmPickerCandidate / fetchDebugArtifact），依赖 `platformSession.token` + `platformProjectId`；会话与采集记录存在平台 DB（debug_sessions / picker_captures），浏览器执行靠绑定 Agent。
- 本机 Worker（server/index.ts）已具备：有头 Chromium（`chromium.launch({ headless: false })`）、run/validation 任务 + SSE + artifacts + fixture 页面、`/health`。
- 已有本地降级先例：元素验证 `confirmValidation` —— 有平台走 `createPlatformElementValidation`，否则走本机 `createValidation` + `subscribeToTask` + `artifactUrl`（`src/pages/ElementsPage.tsx`）。

### A1 方案对比

| 方案 | 做法 | 实现路径 | 改动范围 | 风险 | 对现有功能影响 | 新依赖 |
| --- | --- | --- | --- | --- | --- | --- |
| **A1（推荐）** | 给本机 Worker 增加交互式元素选取能力（移植 Agent picker），前端「从页面获取」已连平台走平台通道、否则降级本机通道 | ① 抽取共享 picker 逻辑（注入脚本 + 候选生成/评分 + 高亮）为 `server/picker-core.ts`，agent 与 server 复用；② server 增加本地调试会话（in-memory）+ picker.enable/captures/preview/confirm(fillback) 路由 + 截图进本地 artifact；③ worker-api.ts 增加对应客户端；④ ElementPickerPanel 抽象 channel（platform/local），ElementsPage 按 `platformProjectContext` 分流；⑤ 本地 confirm 仅返回候选信息（不落库，元素保存仍走抽屉正常保存） | server/picker-core.ts(新)、server/index.ts、src/worker-api.ts、src/pages/ElementPickerPanel.tsx、src/pages/ElementsPage.tsx、测试 | 需要把 Agent 的注入/评分逻辑抽共享并保证两端行为一致；本地会话为内存态（进程重启失效，可接受，属轻量采集） | 平台通道完全不变（同一切口/返回结构）；仅新增本地分支 | 无 |
| **A2** | 未连平台时以本地模式运行 Agent 并直连本机 Worker | 本机 Worker 需要实现 Agent 的 WebSocket 注册/租约/调试会话协议，前端按本地 Agent 接入 | server/index.ts（协议层大改）、agent 兼容模式 | 相当于在本机 Worker 里再造一个迷你平台服务端，复杂度高、边界混乱；与「本地轻量」目标相悖 | 高风险、大范围 | 无 |
| **其它** | 用独立 CDP 控制器直接驱动本机 Chromium | server 内直接 `chromium.connectOverCDP`/`launch` 实现 picker | 与 A1 相似但无共享复用（Agent 逻辑重复维护） | 与 Agent picker 行为易漂移 | 同 A1 | 无 |

**推荐 A1**：复用已验证的 Agent picker 能力 + 现成的本机验证降级先例，改动集中在「本机 Worker 新增 picker 能力 + 前端 channel 分流」，平台通道零改动，不引入新依赖。

### A1 关键设计决策
- **通道选择优先级**：已连平台且项目已导入 → 平台通道（行为完全不变）；否则 → 本机通道（本机 Worker `/health` 在线时可用）；本机 Worker 离线 → 明确提示「本机执行服务未运行，请先启动 npm run server」。
- **环境仍必需**：未选环境 → 保持现有「请先在表单中选择默认验证环境」提示（定位要关联环境 baseUrl）。
- **本地确认只回填不落库**：本地 confirm 仅返回候选 method/value/path/environmentId/建议名称（等同平台 fillback 语义）；「写入元素库」由抽屉保存链路完成（本地 store / 平台同步），避免本地与平台两套写入逻辑。平台 fillback/element/step 三种确认行为与返回结构保持不变。
- **密钥过滤 / 截图 / 内存回收 / 竞态**：沿用现有实现（候选生成含密钥过滤；截图轮询 `URL.revokeObjectURL`；同环境多窗口前端取最新 capture）。
- **权限边界**：本地通道只允许本项目内环境（沿用 run/validation 的 projectId 作用域），不引入认证（本机 API 本就无鉴权，与现有本机通道一致）。

## B. 「发布管理」入口定位与收敛

### B0 现状（证据）
- `sectionMeta.platform = 「发布管理」`；侧边栏可见性：dev 过滤掉 data/agents/debug/automations/governance（保留 platform）；production 按角色（owner/admin 含 data/automations/governance/platform/settings，且**不含 agents/debug**——执行节点/调试在 production 只经平台页可达）。
- `PlatformPage`：local 模式 → `AgentsPage`；platform 模式 → 5 个 Tab：发布与远程运行(AgentsPage)、远程调试(DebugSessionsPage)、数据集(DatasetsPage)、持续回归(AutomationsPage)、治理分析(GovernancePage)。
- 重复点：production 下「数据集/持续回归/系统管理」在侧边栏与平台页 Tab 各出现一次；「执行节点/调试」仅在平台页（production），不重复。
- 真正的发布/回滚操作：FlowsPage（版本发布/回滚）、AgentsPage（发布到 Platform、已发布版本列表），不在 PlatformPage。
- `ProjectShell`：production 下 agents/debug 路由重定向到 overview；非 platform-enabled 项目访问 data/agents/debug/automations/governance 重定向到 /platform。

### B 结论
**「发布管理」命名与内容不符（它是平台/远程能力聚合页，不是发布管理），且在 production 下与侧边栏重复（数据集/持续回归/系统管理）**。它仍是「执行节点/远程调试」在 production 的唯一可达入口，因此不能删除，应**改名 + 收敛**。

### B 方案对比

| 方案 | 做法 | 优点 | 缺点 | 推荐 |
| --- | --- | --- | --- | --- |
| B1（推荐） | 改名「平台」（或「平台与远程」）；production 下平台页 Tab 收敛为「发布与远程运行 + 远程调试」，数据集/持续回归/系统管理以侧边栏为主入口；dev 下保留原 5 Tab（dev 侧边栏本就无这些入口，Tab 是其唯一导航路径，保可达） | 命名贴切；production 单一主入口；dev 可达性/测试不破坏；改动小 | dev 与 production 的 Tab 集合不同（可接受，dev 为开发便利） | ✅ |
| B2 | 保留 5 Tab，把侧边栏的 数据集/持续回归/系统管理 移出 | production 下也单一入口 | 侧边栏是这些功能的主场，移出反而破坏「功能在侧边栏」的既有语义与角色权限矩阵 | 否 |
| B3 | 仅改名，Tab 不动 | 最小改动 | 未解决重复 | 否（作为过渡可接受） |
| B4 | 删除平台页（执行节点/调试并入侧边栏） | 消除聚合页 | production 角色矩阵需重排；执行节点/调试暴露给所有角色与权限模型冲突；改动大、风险高 | 否 |

**推荐 B1**：改名 + production 收敛 + dev 保可达。production 下「远程调试」「发布与远程运行」仍可达（平台页两个 Tab）；数据集/持续回归/系统管理单一主入口在侧边栏；local 与 platform-enabled 两种模式导航自洽（local→执行节点页，platform→两 Tab 平台页）。

### B1 实施要点
- `sectionMeta.platform` label 改「平台」（或「平台与远程」），路由 key 仍为 `platform`（避免破坏现有 URL/路由/测试）。
- `PlatformPage`：production（`import.meta.env.PROD || VITE_AUTH_REQUIRED==="1"`）→ 仅「发布与远程运行 + 远程调试」两 Tab；非 production → 保留 5 Tab（dev 可达性）。
- 不改变 ProjectShell / ProjectLayout 的角色权限矩阵与重定向逻辑；不移动 agents/debug 路由。
