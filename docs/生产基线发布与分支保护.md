## 仓库内门禁

`quality-linux` 在 `ubuntu-latest` 上按本地质量矩阵运行：

```text
npm ci
uv lock --check --project server-py
npm run setup:py
npm run build
npm run lint
npm run test:unit
npm run test:startup
npm run test:py
npm run check:bundle
npx playwright install --with-deps chromium
npm run test:e2e
```

`deployment-windows` 在 `windows-latest` 上使用同一锁定的 Node 依赖安装和 Python 3.12 环境，安装 Chromium 后运行 `npm run test:windows`。该 smoke 会解析 PowerShell 部署脚本、渲染 WinSW 配置，并验证 SQLite 备份/恢复路径。它依赖 `node:sqlite`，所以工作流显式使用 Node 22；产品启动的最低 Node 版本仍以 `package.json` 和生产启动契约为准。

工作流只授予 `contents: read`，不注入生产环境变量、`.env`、数据库、运行产物或生产密钥。GitHub Actions 日志是每一步的首要定位入口；若 Playwright 产生 `playwright-report`，工作流只上传该测试报告，并保留 14 天。

## 发布证据与 tag

候选提交必须满足下列顺序，才能创建 baseline tag：

1. 候选提交的工作区干净，且本地运行记录完整保留。
2. 对该提交的 PR 运行中，`quality-linux` 和 `deployment-windows` 都成功。
3. 上表的分支保护和审核控制已有责任人及可访问证据。
4. 在经过审核的候选提交上创建带注释 tag，例如 `phase0-baseline-YYYYMMDD`，推送后记录 tag 名、commit SHA、Actions URL 和本地门禁记录。

建议由发布责任人执行以下命令，并将输出链接或粘贴到发布记录中：

```bash
git status --short
git rev-parse HEAD
git tag -a phase0-baseline-YYYYMMDD -m "Phase 0 reviewed baseline"
git push origin phase0-baseline-YYYYMMDD
```

tag 仅标识一个可定位的仓库版本，不能代替 GitHub 分支保护、审批或远端门禁的证据。当前尚未满足上述条件时，不得创建或声称存在 Phase 0 baseline tag。

## 发布与回滚记录

每次发布至少记录：候选 SHA、PR、两项 CI URL、审核者、目标主机/包版本、部署时间、健康检查结果、备份位置、回滚决策和实际回滚结果。涉及密钥的字段只记录密钥标识或存放位置，不记录值。

出现例外时，使用以下格式，并在下一个工作日内完成补验或回滚：

```text
日期：
变更 / PR / commit：
被豁免的检查：
业务原因与风险：
批准人：
补验截止时间：
回滚入口与负责人：
证据链接：
```

仓库提供的 Windows 回滚入口是 `scripts/rollback.ps1`；数据库恢复入口是 `scripts/restore.ps1`。它们需要与目标主机上的已验证备份和上一版应用目录一起使用。当前产物目录不一致问题由 `08-19-artifact-backup-health-observability-fixes` 负责，完成前不得把一次脚本执行当作完整截图或 Trace 恢复证明。
