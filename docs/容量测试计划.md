# 容量测试计划（CAP-01）

本文定义确认目标容量所需的负载画像、阈值与证据，但不声称这些结果已在真实硬件上
跑通。真正的 P95 / 错误率 / 队列 / 资源证据必须来自一次受控压测。

## 确认目标

- 单公司、最多 10 个内部工作区，共享一套部署。
- 基线 100 个账户、20 个并发 Web 用户、500 runs/day。
- 全局 runner 并发 2，单工作区并发 1。

## 负载画像

1. 创建 10 个工作区、100 个账户，并按角色分布（每个工作区 1 admin + 若干 member）。
2. 20 个并发会话，按真实比例混合只读（项目列表/运行详情）与写操作（编辑 flow、
   保存、触发 run）。
3. 在运行窗口内提交累计 500 次 run（受全局/工作区并发约束），记录排队与完成曲线。

## 阈值（建议起点）

- API：P95 延迟（只读）<= 500ms，P95（保存/触发）<= 2s。
- 错误率：<= 1%（HTTP 5xx / 断言失败）。
- 队列：在全局/工作区上限下无饿死、无重复完成、无跨工作区误取消。
- 资源：磁盘在保留 + 备份后仍留充足余量；内存/CPU 无持续饱和。
- 成功率：500 runs 中 >= 99% 完成（success/failed 均为完成态，不卡 running）。

## 证据要求

- 压测机与部署机硬件、网络、操作系统与并发参数。
- 每项阈值对应的实测值（P95、错误率、队列深度、磁盘/内存/CPU）。
- 一段有代表性的 soak 记录（正常、降级与恢复三种状态均被正确观测）。

## 执行入口

`scripts/ops/capacity-smoke.py <base-url>` 会用一个 bootstrap 账户创建 10 个工作区、
100 个账户并触发一批 run，输出各步骤耗时与成功/失败计数，作为压测的骨架。它需要
真实部署与 `AUTOFLOW_SMOKE_EMAIL`/`AUTOFLOW_SMOKE_PASSWORD`，不能在仓库内伪造结果。
