# AutoFlow 数据迁移与回滚方案

## 目标

本方案用于将旧版 `project_documents` 和浏览器项目数据迁移到资源级表，同时保留可验证、可重复执行和可回滚的路径。迁移期间 SQLite 仍是唯一服务端事实来源。

## 上线前准备

1. 停止 AutoFlow 服务，确认没有运行中的 Chromium 任务。
2. 使用 `scripts/backup.ps1` 执行 SQLite 一致性备份并校验 `PRAGMA integrity_check`。
3. 记录当前应用版本、`schema_migrations` 最大版本和备份目录。
4. 在恢复演练目录运行 `scripts/restore.ps1`，确认备份能够启动旧版本。

## 数据迁移

- 数据库迁移按版本号在单个事务中顺序执行；任一步失败都会回滚该版本并阻止服务启动。
- `project_documents` 只读保留至少一个版本周期。资源迁移以项目 ID 和资源 ID 为幂等键，重复执行不会创建副本。
- 浏览器导入使用工作空间和 `sourceId` 作为幂等键。导入成功后客户端只保留 UI 偏好以及与服务端版本绑定的未提交草稿。
- 迁移完成后对每个项目比较流程、元素、变量、环境数量，并验证流程中的元素引用均能解析。
- 密钥只迁移名称等元数据；明文必须通过密钥接口重新加密写入，不能进入资源快照或迁移日志。

## 灰度与回滚

- `AUTOFLOW_RESOURCE_API_ENABLED=0` 可在迁移窗口内临时关闭资源 API 写入；正式上线后保持开启。
- 若迁移失败，服务不会写入后续版本。修复迁移代码后可基于同一数据库重试。
- 若上线验证失败，停止服务，将失败数据库移至隔离目录，通过 `scripts/restore.ps1` 恢复上线前备份，再启动上一应用版本。
- 禁止直接复制仍带有未 checkpoint WAL 的数据库文件，也禁止人工修改 `schema_migrations` 伪造成功状态。

## 验证清单

- 空数据库可以从版本 0 升级到最新版本。
- 现有数据库可以升级，连续启动两次不会重复迁移。
- 清空浏览器存储后，重新登录仍可读取所有项目资产。
- 同一资源的旧版本更新返回冲突，不会静默覆盖。
- 已发布 Revision、审计记录和运行产物关联在迁移前后保持不变。
- 恢复后的数据库通过 `PRAGMA integrity_check`，项目抽样和登录执行链路通过。
