# 参考 ntest 重构 ui_auto 为可用项目

## Goal

把 `ui_auto` 从当前“功能很多但用户无法稳定完成一次真实自动化”的状态，重构为可安装、可启动、可操作、可验证的 Web UI 自动化项目。最终用户应能在本地或内网部署后，用浏览器完成：创建项目 → 录制或配置步骤 → 保存流程 → 在目标页面执行 → 查看清晰的成功/失败结果与证据。

`ntest` 作为产品和工程参考，吸收其可验证的领域模型、录制/定位、异步执行、断言和报告体验；不在未取得源码和许可证确认前复制其代码或强行迁移技术栈。

## Background And Confirmed Facts

- 当前仓库是单体项目：React 19 + TypeScript + Vite + Ant Design + Zustand/TanStack Query 前端，FastAPI + SQLite + Playwright 后端。
- 生产入口是 `npm run start`，要求构建产物和 `PLATFORM_SECRET_KEY`；服务默认监听 `127.0.0.1:8787`，可配置为局域网访问。
- 当前代码已包含登录、工作区/项目隔离、流程/元素/变量/环境、录制、ManagedRunner 执行、运行事件、截图/Trace、断言、模板、定时任务和通知等能力，并有较完整的 Vitest、pytest、Playwright 测试集。
- README 将产品定位为内网单机部署的自动化工作台，浏览器执行发生在部署机，不依赖远程 Agent。
- 当前环境无法解析 `github.com`，因此本轮不能直接拉取 `https://github.com/rebort-hub/ntest.git`；参考项目的具体行为和代码仍需通过可访问源码、压缩包或用户提供的关键文件确认。

## Product Requirements

### R1 可用性优先的核心闭环

优先保证新用户在干净环境中能够完成最小闭环，并在每一步得到可理解的状态、错误和恢复动作：安装依赖、初始化配置、启动服务、登录、创建项目、创建/录制流程、保存、执行、查看结果。不能以“接口返回成功”替代浏览器端可完成的真实操作。

### R2 参考 ntest 的能力映射

建立当前项目与 `ntest` 的能力/架构差距矩阵，区分“已有但断裂”“缺失且属于 MVP”“可延后增强”。对参考项目的吸收必须落到本项目的领域模型、API 契约、前端状态和测试验收上，而不是只做页面改名或视觉复制。

### R3 录制、定位与执行可靠性

录制结果必须能稳定转换为可编辑步骤；步骤保存后的执行必须使用同一份规范化定义；元素定位失败时要提供候选、原因和可修复路径；运行需要有明确的排队/执行/成功/失败/取消状态，并保留足够证据定位问题。

### R4 断言与报告一致性

录制、编辑器、执行器和报告使用同一套可版本化断言语义；旧流程快照可继续读取。失败结果至少要显示失败步骤、断言期望/实际值和可用截图或日志引用。

### R5 部署与数据安全边界

保留当前登录、工作区/项目隔离、服务端密钥托管和部署机执行边界。除非规划阶段基于证据证明必要，不默认引入 MySQL、Redis、Celery、外部 AI 或远程 Agent。

### R6 渐进式交付

将重构拆成可独立验收和回滚的阶段；每阶段必须有代码级测试和至少一条真实浏览器或 API 闭环证据。优先修复阻断核心闭环的问题，再扩展高级能力和视觉细节。

### R7 第一阶段硬目标（已确认）

用户已确认第一阶段必须交付 R1-R5 对应的五项能力：

1. 可重复的一键可用闭环。
2. 智能录制结果整理。
3. 定位器候选与启发式自愈。
4. 统一流程和断言契约。
5. 可解释的执行反馈。

数据驱动/环境增强和编排体验优化（候选能力第 6、7 项）不作为第一阶段完成条件，可在后续阶段单独规划。

## Candidate New Capabilities

以下是规划阶段识别出的“新增或实质增强”候选，不把当前已有页面简单改名当作新功能：

- **可重复的一键可用闭环**：首次运行检查依赖、密钥、浏览器和数据库，提供明确的修复提示；内置本地 fixture 和可重复验收入口。
- **智能录制结果整理**：把录制事件转换为去重、可编辑、带候选定位器和风险提示的步骤；录制会话支持暂停/恢复，服务重启后显示已中断而不是丢失。
- **定位器候选与启发式自愈**：为元素保存主定位器和候选定位器，执行时按唯一匹配和稳定性评分选择，并在报告中说明实际采用的定位器；不依赖外部 AI。
- **统一的流程/断言契约**：步骤、元素、断言、环境和运行快照使用同一套版本化 schema，编辑器保存的内容与执行器读取的内容保持一致，旧快照可继续运行。
- **可解释的执行反馈**：运行队列、实时事件、失败步骤、期望/实际值、截图/Trace、重试和取消形成一条完整链路；支持按流程/环境/数据集查看历史趋势。
- **数据驱动和环境切换的闭环验证**：数据集版本在运行时冻结，环境变量和密钥按项目边界注入，结果可追溯到具体数据行和环境。
- **面向维护的编排体验**：步骤拖拽/批量编辑、元素重复与歧义提示、断言配置校验、保存即校验/运行前预览，减少“配置成功但运行才发现错误”。

其中，项目/流程/元素/变量/环境、基础录制、运行、断言、定时任务和通知已有部分实现；本次工作的新增价值主要是上述能力之间的贯通、可靠性和可验证性。

## Acceptance Criteria

- [ ] 有一份基于可获得 `ntest` 资料和当前代码证据的能力/架构差距矩阵，标注证据来源和不确定项。
- [ ] 干净环境按文档执行安装、配置、构建和启动命令，服务能成功提供登录页面；缺配置时能给出明确修复提示。
- [ ] 新建用户可在浏览器中创建项目和流程，保存后刷新仍能看到同一份数据，不依赖演示数据或 local fallback。
- [ ] 至少一个本地 fixture 目标页面可通过录制或手工步骤执行成功；失败场景能在运行详情看到失败步骤、原因和证据。
- [ ] 流程步骤、元素定位、断言和运行结果在前后端之间使用有明确版本/兼容策略的契约，并有回归测试。
- [ ] 核心闭环具备可重复的单元、后端和 Playwright 验收命令；所有与本次改动相关的检查通过。
- [ ] 交付文档说明已实现范围、未实现范围、部署方式、已知限制和回滚点。

## Scope Boundaries

### In Scope

- 核心闭环的阻断问题定位与修复。
- 与 `ntest` 的领域能力映射、必要的数据/API/状态重构。
- 录制/定位/执行/断言/报告在 MVP 范围内的契约统一。
- 可重复的本地 fixture、启动检查和端到端验收。
- 与上述行为直接相关的 UI 可用性改造。

### Out Of Scope Unless Evidence Requires It

- 在无法核实源码/许可证前照搬 `ntest` 代码。
- 一次性迁移到 Vue、Celery、Redis、MySQL 或多机 Agent 架构。
- 外部商业 AI、自愈模型训练、跨设备执行和云端 SaaS 化。
- 与核心闭环无关的全量视觉重做、营销页和非阻断高级报表。

## Open Decisions

- 第一阶段是否把“单机本地 fixture 的完整闭环”作为唯一硬验收目标，真实业务网站/内网网站验证作为后续补充。该选择会决定第一阶段的 fixture、浏览器权限、部署验证和优先级。
