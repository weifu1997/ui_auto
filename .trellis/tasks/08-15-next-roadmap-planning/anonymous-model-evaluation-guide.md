# 四模型匿名评测执行手册与评分表

## 1. 推荐评测方式

推荐进行两轮单项盲测，而不是只做一次联合任务：

- 第一轮：四个模型都使用 `anonymous-model-prompt-batch-execution.md`。
- 第二轮：四个模型都使用 `anonymous-model-prompt-recording.md`。
- 可选第三轮：使用 `anonymous-model-prompt-combined.md`，评估长程任务持续性和任务取舍。

单项结果能区分数据库/并发正确性与浏览器/安全能力。联合评测容易因为固定时限只完成前半项，不能公平说明模型对另一项的能力。

## 2. 公平性协议

### 仓库基线

1. 从同一个 Git commit 和同一份已批准计划创建四个独立副本或 worktree。
2. 基线必须干净，不能包含其他模型的代码、测试缓存、本地数据库或浏览器 profile。
3. 给每个模型相同的 CPU、内存、磁盘、网络策略和命令权限。
4. 使用同一 Node、npm、Python 和 Playwright 浏览器版本。
5. 先由评测者在每个副本运行一次基线门禁，记录初始通过/失败；基线不同则该轮作废。

### 时间和交互

- 单项建议上限：8 小时或固定 token/费用预算，取先到者。
- 联合建议上限：16 小时。
- 四个模型使用相同思考强度、上下文限制和工具权限。
- 不提供中途人工提示，不回答模型澄清问题；Prompt 已授权其自主决策。
- 模型结束或超时后立即冻结工作区。评测阶段不允许模型继续修复。

### 匿名与隔离

- 随机标记为 M1-M4，评分者看不到供应商和模型名称。
- 每个模型不能读取其他副本、共享日志或评分结果。
- 自动评分先于人工代码审查，人工评分时隐藏模型身份和最终自评文字。
- 模型自报测试通过不计分，只采信评测者在冻结工作区重跑的结果。

## 3. 评测者执行流程

1. 保存模型最终回复、完整 diff、`git status --short` 和工具日志。
2. 检查是否修改/删除既有测试、提交 secret、写入数据库/缓存/浏览器 profile。
3. 在新临时数据目录和空浏览器状态运行 build、lint、unit、Python、E2E、Windows smoke。
4. 运行评分者隐藏测试。隐藏测试只验证公开计划中的契约，不增加新需求。
5. 对前端使用桌面和窄屏至少各做一次黑盒检查：无重叠、按钮状态正确、错误可理解。
6. 评分者阅读关键 diff，检查事务、权限、敏感数据、竞态和回滚边界。
7. 两名评分者独立给主观项评分；相差超过 3 分的项共同复核证据。
8. 记录总分、硬性封顶、完成时间、工具调用量/费用和一次通过率。

## 4. 通用评分原则

- 每项只按可运行代码和测试证据评分，文档描述不能替代实现。
- 一项存在但明显不可达、使用 mock 数据或只完成 UI，按未实现计算。
- 新增测试如果只断言模型自己硬编码的结果、删除功能后仍会通过，按无效测试计算。
- 基线既有失败不扣模型分，但模型引入的新失败按对应项扣分。
- 最终总分为功能分减处罚分，最低 0 分。

## 5. 批量执行评分表（100 分）

| 类别 | 分值 | 评分要点 |
| --- | ---: | --- |
| Revision 正确性 | 12 | 单运行按 flow/environment 解析；A/B 回归；显式 revision 一致性；所有入口覆盖 |
| Schema 与兼容 | 8 | 可重复 migration；历史 run 可读；nullable 关联和索引；不破坏旧 API |
| 原子创建与预检 | 15 | 全量预检；单事务 batch+runs+events；失败零写入；限制在服务端 |
| 幂等与并发 | 12 | 数据库唯一约束；相同 key 等价返回；不同 payload 409；并发只创建一次 |
| 状态聚合与恢复 | 10 | 正确六状态/counts；SQL/服务层唯一 owner；重启恢复 queued；顺序稳定 |
| 取消与重试 | 10 | 条件更新；竞态安全；幂等取消；retry failed/canceled；新 batch/最新 revision |
| API、权限与审计 | 8 | create/list/detail/cancel/retry；分页；跨项目隔离；真实 batch 审计；无敏感 snapshot |
| 前端体验 | 10 | 流程多选、确认、串行提示、错误定位、运行中心分组、孤立 run、刷新恢复 |
| 测试质量 | 10 | migration/service/concurrency/recovery/frontend/E2E；断言行为而非实现细节 |
| 工程质量与报告 | 5 | 复用现有模式、范围克制、可维护性、无无关改动、报告真实完整 |

### 批量执行隐藏测试建议

- 流程 A 先保存、B 后保存，运行 A 的 snapshot.flow.id 必须是 A。
- 20 个合法 flow 成功，21 个或 2001 总步骤失败且零写入。
- 在两个线程/请求中同时提交同 key，只有一个 batch 和 N 个 runs。
- 同 key 不同 flowIds 返回冲突。
- 第 2 个 run 失败，第 3 个仍运行，batch 为 partial_failed。
- 取消时一个 running、两个 queued、一个 success，检查最终状态不覆盖 success。
- 原 batch 失败后发布新 revision，retry 使用新 revision。
- 提交事务后不 enqueue，重启服务，所有 queued run 恢复且无重复。
- 历史 unbatched run 在分页和详情中仍可见。

### 批量执行硬性封顶

- 仍可能运行错误流程 revision：总分最多 35。
- 用前端循环单运行 API，或 batch 仅在内存/前端：总分最多 30。
- 创建不是全有或全无，预检失败留下部分 runs：总分最多 45。
- 没有服务端持久幂等，重复请求产生重复执行：总分最多 55。
- 绕过权限或可读取/操作跨项目 batch：总分最多 40。
- 改为无边界并行并破坏单并发约束：总分最多 50。

## 6. 流程录制评分表（100 分）

| 类别 | 分值 | 评分要点 |
| --- | ---: | --- |
| 浏览器会话与生命周期 | 10 | 有头 Chromium；init script；状态机；单活动会话；超时/关闭释放 |
| 事件捕获与归并 | 18 | click/input/select/check/key/navigation；输入合并；因果去重；pause/stop flush |
| seq 与可靠传输 | 7 | 单调 seq；afterSeq；重复轮询无重复；bounded log/limit |
| 定位器与元素 | 12 | 复用 Picker；role+name；唯一性；元素去重/唯一命名；步骤引用资产 |
| 敏感数据安全 | 15 | 页面侧不发送；后端再判定；绑定 secret variable；API/log/store/storage/revision 无明文 |
| 认证与 API | 8 | 平台 session、flow.edit、项目/环境、URL 校验；状态和幂等命令；不扩大 legacy API |
| 编辑器体验与原子导入 | 10 | 控制、状态、review、warning、绑定阻断、一次性追加、取消零副作用 |
| 保存与重放闭环 | 8 | 保存进入现有同步/revision；ManagedRunner 在本地 fixture 成功重放 |
| 测试质量 | 8 | normalizer、API、真实 Chromium、React、E2E、安全泄漏检查 |
| 工程质量与报告 | 4 | 共享会话而非复制、范围克制、兼容 Picker、无无关改动、报告真实 |

### 录制隐藏测试建议

- 在 input 输入 10 个字符，只生成一个填写步骤。
- Password 使用独特 canary，扫描 API 响应、捕获日志、SQLite、local/session storage、snapshot 和 diff，不能出现 canary。
- select/checkbox 只生成语义动作，不额外生成 click。
- 点击按钮导航不重复 open；直接 `page.goto` 或测试页 location 导航生成 open。
- 完整 reload 后继续捕获；SPA history change 行为符合公开契约。
- 相同 afterSeq 请求两次，前端 store 不重复步骤。
- pause 期间操作不产生步骤，resume 后 seq 连续；stop 两次结果一致。
- 两个相同文本按钮时 role 需含 accessible name 或阻止非唯一导入。
- 取消 review 后 flow/element 数量和 sync 请求不变。
- iframe/file input 产生 warning，不生成假成功步骤。
- 未认证、跨项目和非法 URL 被拒绝，legacy Worker 网络策略不改变。
- E2E 录制、导入、保存后实际 runner 成功操作本地 fixture。

### 流程录制硬性封顶

- Password 或 secret canary 离开页面、进入 API/日志/持久状态：总分最多 20，并标记安全失败。
- 录制 API 未认证或存在跨项目控制：总分最多 30。
- 只做 UI/mock，没有真实 Chromium 连续捕获：总分最多 25。
- 录制结果不能由现有 runner 重放：总分最多 50。
- 取消录制仍写入元素/流程：总分最多 55。
- 扩大 legacy Worker API 对内网/公网暴露：总分最多 40。

## 7. 通用处罚（可累计，最多扣 30 分）

- 删除、跳过或实质放宽已有测试：每项 -10。
- 提交真实 secret、数据库、profile、依赖缓存或大型生成产物：-10；真实 secret 同时按安全封顶。
- 回滚或覆盖无关用户改动：-5 至 -15。
- 最终声称某命令通过，但评测日志证明未运行或失败：每项 -3，最多 -10。
- 新增未经批准的重依赖或大范围无关重构：-3 至 -10。
- 仓库无法 build 或服务无法启动：除对应功能失分外再 -10。

## 9. 排名方式

默认按单项总分排名。若需要综合排名：

```text
综合分 = 批量执行分 × 45% + 流程录制分 × 45% + 效率分 × 10%
```

效率分不要只奖励速度，建议为：

- 5 分：在时限内完成且无不实测试报告。
- 3 分：成本/工具调用处于四模型前二。
- 2 分：首次冻结版本的隐藏测试通过率处于前二。

安全封顶优先于综合加权。任何模型在录制中泄漏敏感值，不能因批量执行高分成为综合第一。
